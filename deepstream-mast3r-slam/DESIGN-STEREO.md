# Гибрид: моно-SLAM по левой камере + стерео для метрического масштаба

Ветка `claude/gstreamer-nvinfer-stereo-hybrid-g29qxg`. Цель — **точная метрическая
траектория и карта для внедорожной навигации** на чисто визуальных данных
(стереопара), с замыканием круга (loop closure) с минимальной ошибкой.

> Терминология честно: без IMU это **стерео-VO/SLAM**, а не VIO. Инерциальный
> датчик в конвейер не заведён (возможное расширение — отдельный side-channel).
> Что даёт наш стек: метрический масштаб от стереобазы + глобальная оптимизация
> с loop closure, т.е. основные источники дрейфа моно-SLAM устранены.

---

## 1. Почему у моно-SLAM «плывёт» круг и что чинит стерео

Моно-SLAM оценивает позы в **Sim3** (с точностью до масштаба): масштаб карты не
наблюдаем из одной камеры и дрейфует вдоль трека. На километровом круге по
пересечённой местности это главный источник невязки при замыкании.

Стереопара убирает эту степень свободы: **база между камерами известна в
метрах**. MASt3R по паре (L,R) оценивает взаимную позу камер; отношение
`baseline_true / baseline_estimated` — это точный коэффициент масштаба карты в
данный момент. Привязывая масштаб на каждом ключевом кадре, мы:

* фиксируем метрическую шкалу всей траектории (навигация в метрах);
* убираем дрейф масштаба → при замыкании круга остаётся только SE3-невязка,
  которую снимает глобальная Gauss-Newton-оптимизация.

## 2. Архитектура

```
v4l2 (левая)  ─┐
               ├─ nvstreammux(batch=2) ─ nvinfer(энкодер, batch=2) ─ nvdsmast3rslam(stereo-mode)
v4l2 (правая) ─┘        │                       │ NvDsInferTensorMeta(feat,pos) на каждый кадр батча
                        ▼                       ▼
              кадры спарены по source-id   ┌──────────────────────────────────────────┐
                                           │ КАЖДЫЙ КАДР: моно-трекинг по ЛЕВОЙ камере │
                                           │   decoder(frame, keyframe) → match → Sim3 │
                                           ├──────────────────────────────────────────┤
                                           │ КЛЮЧЕВОЙ КАДР (редко):                    │
                                           │  1) стерео: decoder(L,R)+decoder(R,L)     │
                                           │     → Umeyama(X_R^R → X_R^L) → T_LR       │
                                           │     → s = baseline / ‖t_LR‖ (EMA)         │
                                           │     → карта ключевого кадра в МЕТРАХ      │
                                           │  2) loop closure: глоб. дескриптор        │
                                           │     (mean-pool ViT-токенов) → кандидаты   │
                                           │     → симметричный матчинг → рёбра графа  │
                                           │  3) backend: gauss_newton_rays (CUDA)     │
                                           │     по всем ключевым кадрам               │
                                           └──────────────────────────────────────────┘
```

Ключевые решения:

* **Трекинг остаётся монокулярным по левой камере** (как в эталоне) — правая
  камера не участвует в покадровом трекинге, поэтому стоимость на кадр не
  растёт. Вся «стерео-работа» происходит только на ключевых кадрах.
* **Оценка масштаба.** На ключевом кадре выполняются два прогона декодера:
  `decoder(L,R)` даёт точки правого вида в системе левой камеры (X_R^L),
  `decoder(R,L)` — те же точки в системе правой камеры (X_R^R). Взвешенное
  (по уверенности) выравнивание Umeyama X_R^R → X_R^L даёт T_LR; норма его
  трансляции — оценка базы в «единицах MASt3R». Коэффициент
  `s = baseline / ‖t_LR‖` сглаживается EMA с отбраковкой выбросов и применяется
  к каноническому пойнтмапу ключевого кадра. Дополнительно стерео-пойнтмап
  (s·X_L^L) вливается в карту ключевого кадра через штатный weighted-фильтр —
  карта получает независимое стерео-наблюдение глубины.
* **Loop closure (C++-порт, без ASMK).** Оригинальный ретривер (ASMK) —
  большая Python-зависимость; вместо него — лёгкий глобальный дескриптор:
  L2-нормированный mean-pool токенов ViT-энкодера (1024-D на ключевой кадр).
  Кандидаты — топ-1 по косинусной близости среди кадров старше `loop-min-gap`,
  порог `loop-sim-thresh`. Кандидат проверяется геометрически (симметричный
  матчинг, порог доли валидных соответствий) — ложные срабатывания отсекаются.
* **Backend.** Порт `FactorGraph.add_factors + solve_GN_rays`: рёбра
  (последовательные + loop) складываются в граф, глобальная оптимизация — тем
  же CUDA-ядром `gauss_newton_rays_cuda`, что и в эталоне (оно уже
  компилируется в наш `.so`). Первый ключевой кадр закреплён (pin=1). Запуск —
  синхронно при создании ключевого кадра: на 1660 Ti это даёт «икание» FPS на
  ключевых кадрах, но гарантирует, что к концу трека карта согласована.

## 3. Требования к стереопаре

* **Синхронизация затворов** L/R (аппаратный trigger или общий clock). Для
  внедорожки с вибрациями — критично: рассинхрон 10 мс на скорости 30 км/ч —
  это 8 см ложной базы.
* **Жёсткая база**, известная в метрах (свойство `baseline`). Ректификация НЕ
  нужна — MASt3R работает с произвольной относительной позой камер.
* Перекрытие полей зрения; глобальный затвор предпочтителен (rolling shutter
  на вибрации портит геометрию).

## 4. Свойства элемента (добавленные)

| Свойство | По умолчанию | Назначение |
|----------|--------------|-----------|
| `stereo-mode` | `false` | включает спаривание кадров батча и стерео-масштаб |
| `baseline` | `0.12` | база стереопары, **метры** |
| `left-source-id` / `right-source-id` | `0` / `1` | source-id левой/правой камеры в `nvstreammux` |
| `loop-closure` | `true` | ретривер + факторный граф + глобальная GN |
| `loop-sim-thresh` | `0.90` | порог косинусной близости глобальных дескрипторов |

Если в батче пришёл только левый кадр (правая камера отвалилась) — элемент
деградирует в моно-режим, трекинг не прерывается (масштаб держится на последнем
EMA-значении).

## 5. Запуск

```bash
# конфиг энкодера с batch-size=2: configs/config_infer_mast3r_encoder_stereo.txt
bash deepstream-mast3r-slam/pipelines/run_stereo_v4l2.sh /dev/video0 /dev/video1 0.12
# выход: logs/stereo.txt (метры!), logs/stereo.ply
```

## 6. Ограничения / валидация

* Численные компоненты, требующие проверки на целевом GPU: Umeyama-масштаб на
  реальной паре, порог `loop-sim-thresh` (зависит от сцены), поведение EMA при
  езде по однородной местности (мало текстуры → шумная база).
* Backend синхронный → на ключевых кадрах кадр обрабатывается дольше
  (декодер×2(стерео) + декодер×2(loop-кандидат) + GN).
* IMU не интегрирован (см. преамбулу): при длительной потере текстуры (снег,
  грязь на объектив) одометрию нечем «подхватить».
* Память 1660 Ti: граф держит `X_canon`(2.4 МБ) + `C`(0.8 МБ) + `feat`(3 МБ) на
  ключевой кадр → ~150–300 ключевых кадров в 6 ГБ с учётом движков. Для длинных
  маршрутов — прореживать вход и повышать порог создания ключевых кадров.
