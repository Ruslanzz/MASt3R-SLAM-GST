# GStreamer-плагин для MASt3R-SLAM — проектное решение

Документ описывает архитектуру плагина, обоснование выбора способа запуска
модели (**CUDA vs TensorRT**), выбор источника входных данных и соответствие
выходных данных эталонному репозиторию.

---

## 1. Что делает эталонный репозиторий

MASt3R-SLAM — это **монокулярный** плотный SLAM. Ключевой нейросетевой блок —
двухвидовая модель MASt3R (`AsymmetricMASt3R`):

```
                 ┌──────────────────────────────────────────────┐
   img (1×3×H×W) │  _encode_image  → feat (1×N×1024), pos (1×N×2) │   общий ViT-L энкодер
                 └──────────────────────────────────────────────┘
                          │ feat_i, feat_j (асимметрично, в двух порядках)
                          ▼
                 ┌──────────────────────────────────────────────┐
                 │  _decoder + _downstream_head (DPT)            │
                 │  → pts3d X, conf C, desc D, desc_conf Q       │
                 └──────────────────────────────────────────────┘
```

Поверх сети работает геометрическая часть SLAM, **не являющаяся нейросетью**:

* `mast3r_slam/matching.py` + `matching_kernels.cu` — сопоставление дескрипторов
  (итеративный поиск в окне), собственные CUDA-ядра;
* `mast3r_slam/tracker.py` — оптимизация относительной позы Sim3 (Gauss-Newton,
  Cholesky на torch);
* `mast3r_slam/global_opt.py` + `gn_kernels.cu` — глобальная оптимизация факторного
  графа, собственные CUDA-ядра (`mast3r_slam_backends.gauss_newton_rays/calib`);
* `mast3r_slam/retrieval_database.py` — ASMK-ретривер (loop closure);
* `lietorch` — группы Ли (Sim3/SE3) с собственными CUDA-расширениями.

**Вывод 1.** Нейросеть — это только часть конвейера. Вся геометрия и оптимизация
завязаны на `torch`, `lietorch` и собственные CUDA-ядра, скомпилированные как
PyTorch-расширение. Их перенос на TensorRT невозможен в принципе (TensorRT — это
инференс-движок для сетей, а не фреймворк линейной алгебры/оптимизации).

### Выход эталона (его требуется повторить)

`mast3r_slam/evaluate.py`:

* `save_traj` → `<seq>.txt` в формате TUM: `timestamp tx ty tz qx qy qz qw`;
* `save_reconstruction` → `<seq>.ply` (цветное облако точек, отфильтрованное по
  порогу уверенности `C_conf_threshold = 1.5`);
* `save_keyframes` → PNG ключевых кадров.

Плюс онлайн-поток поз (в репозитории — окно визуализации). В плагине онлайн-поток
реализован как сообщения на шину GStreamer (`mast3r-slam-pose`), а файлы
`.txt/.ply/.png` сохраняются по EOS — **бит-в-бит та же функция `eval.save_*`**.

## 2. CUDA vs TensorRT — взвешивание «за» и «против»

Вопрос «на чём гонять модель внутри плагина» распадается на два независимых:
**(A)** чем считать нейросеть MASt3R, **(B)** чем считать геометрию/оптимизацию.
По пункту (B) альтернатив нет — только CUDA/torch (см. Вывод 1). Поэтому
сравнение касается только нейросетевого блока (A).

### Вариант 1. Чистый CUDA (PyTorch), как в репозитории

| За | Против |
|----|--------|
| Повторно используется **весь** код репозитория без переписывания → выход **идентичен** эталону (главное требование заказчика). | Выше латентность и потребление памяти, чем у оптимизированного TensorRT-движка. |
| Корректно работают динамические формы, двойной асимметричный прогон декодера, AMP-autocast, DPT-головы, RoPE-позиционирование. | Тяжёлый рантайм (PyTorch+cuDNN) внутри DeepStream-контейнера. |
| Геометрия и сеть живут в одном адресном пространстве — нет копирований тензоров туда-обратно. | GIL/Python накладывают оверхед (минимизируется тем, что вся тяжёлая работа — в CUDA, GIL отпускается). |
| Минимальный риск разработки, лёгкая синхронизация с upstream. | Не использует Tensor Cores так агрессивно, как TRT FP16/INT8. |

### Вариант 2. TensorRT для нейросети

| За | Против |
|----|--------|
| Низкая латентность энкодера/декодера (FP16/INT8, Tensor Cores), меньше памяти. | **Сложный и рискованный экспорт.** MASt3R = CroCo/DUSt3R-семейство: RoPE-позиционирование, маскируемое cross-attention, DPT-головы, динамическое число токенов — ONNX-экспорт капризен. |
| Нативная интеграция с `nvinfer` (Gst-nvinfer) в DeepStream. | Декодер прогоняется **дважды** на пару в двух порядках (асимметрия) — не ложится в один `nvinfer`-инстанс с единым layout. |
| Хорошо для edge/embedded (Jetson). | **Выход перестаёт совпадать с эталоном**: FP16/INT8 меняет численность; сопоставление дескрипторов и оптимизация поз чувствительны → траектория «поедет». |
| | TRT ускоряет только сеть; геометрия всё равно на CUDA/torch → всё равно гибрид, всё равно нужен torch в контейнере. Round-trip тензоров TRT↔torch. |
| | Долгая разработка/отладка, привязка движка к версии TRT и GPU (`.engine` непортируем). |

### Вывод 2 — выбранная стратегия

> **По умолчанию — CUDA (PyTorch). TensorRT — опциональный ускоритель только для
> ViT-энкодера, остальное (декодер, головы, геометрия) остаётся на CUDA.**

Обоснование:

1. **Требование «выход такой же, как в репозитории»** выполняется только при
   полном переиспользовании кода → backend по умолчанию = CUDA.
2. Энкодер `_encode_image` — **самый тяжёлый и самый «статичный»** кусок: на
   каждый кадр он считается один раз при фиксированном входе 512×384 (фикс. число
   токенов). Это **единственная** часть, которую безопасно и выгодно вынести в
   TensorRT, не ломая логику SLAM. Декодер/головы оставляем на torch, поэтому
   асимметрия и динамика не мешают.
3. Геометрия принципиально остаётся на CUDA — переносить её на TRT смысла нет.

Архитектура плагина это отражает: backend инференса — **подключаемый**
(`backends/`), с реализациями `torch_cuda` (по умолчанию) и `tensorrt_encoder`
(опционально). Переключение — свойством элемента `backend=torch|tensorrt`.

Полностью-`nvinfer`-вариант (вся сеть как TRT-движок под Gst-nvinfer) сознательно
**не** выбран: он не даёт идентичного выхода и требует переписать матчинг,
трекинг и backend SLAM на C++/CUDA вне torch — это другой проект, а не плагин
«на основе данного репозитория».

## 3. Выбор входа: v4l2 / видеофайл / UDP — «реши что лучше»

MASt3R-SLAM — **монокулярный**. «Пара изображений», нужная двухвидовой модели,
формируется **внутри** алгоритма (текущий кадр ↔ опорный ключевой кадр), ровно
как в эталоне. Поэтому правильная трактовка «пары на входе» — это **один**
видеопоток, а пару строит сам элемент.

**Решение: один монокулярный поток, источник — любой из трёх транспортов**, через
стандартный выбор источника GStreamer/DeepStream. Это:

* совпадает с природой алгоритма (моно) → даёт идентичный эталону выход
  (траекторию);
* покрывает все три запрошенных случая:
  * **v4l2-камера** — `v4l2src` (USB) или `nvv4l2camerasrc` (CSI/Argus на Jetson);
  * **видеофайл** — `filesrc`/`nvurisrcbin`/`uridecodebin3`;
  * **UDP** — `udpsrc ! rtpjitterbuffer ! rtph264depay ! ...` или `rtspsrc`.

Сам элемент `mast3rslam` — `GstBase.BaseTransform` в режиме passthrough: принимает
`video/x-raw, format={RGBA,RGB}` (после `nvvideoconvert`), считает SLAM,
**пропускает буфер дальше без изменений** (чтобы работали официальные NVIDIA-плагины
вниз по конвейеру: `nvosd`, кодеки, синки), а позы публикует сообщениями на шину.

> Настоящая стерео-/двухкамерная «пара» (две независимые камеры в `nvstreammux`
> batch=2) — это уже двухвидовая реконструкция, а не данный SLAM, и она **не**
> даёт совпадающую с эталоном траекторию. Поэтому она вне области этой задачи;
> в `pipelines/` показано, как при необходимости подать две камеры, но штатный
> режим — моно.

Почему именно DeepStream-источники: заказчик указал, что в финальном конвейере
будут официальные NVIDIA-плагины. `nvvideoconvert`/`nvstreammux`/`nvv4l2*`
работают с NVMM-памятью на GPU; перед нашим элементом ставится
`nvvideoconvert ! video/x-raw,format=RGBA` (NVMM→system) — Python-элемент
маппит системную память в numpy. Это прагматичный путь; нулевое копирование на GPU
(CUDA-маппинг NVMM в Python) возможно, но усложняет код и вынесено в раздел
«дальнейшие улучшения».

## 4. Архитектура плагина

```
                       GStreamer pipeline (GStreamer 1.24, DeepStream 9.0)
  ┌───────────┐   ┌────────────────┐   ┌───────────────────────┐   ┌──────────────┐
  │  source   │──▶│ nvvideoconvert │──▶│  mast3rslam (Python)   │──▶│ downstream   │
  │ v4l2/file │   │  → RGBA system │   │  BaseTransform,        │   │ nvosd/enc/   │
  │ /udp/rtsp │   │  память        │   │  passthrough           │   │ sink/fakesink│
  └───────────┘   └────────────────┘   └───────────┬───────────┘   └──────────────┘
                                                    │ bus message "mast3r-slam-pose"
                                                    │ + по EOS: <seq>.txt/.ply/keyframes
                                                    ▼
                                        ┌───────────────────────┐
                                        │ Mast3rSlamRunner       │  (переиспользует
                                        │  ├─ backend (CUDA|TRT) │   mast3r_slam.*)
                                        │  ├─ FrameTracker       │
                                        │  ├─ FactorGraph (CUDA) │
                                        │  └─ SharedKeyframes    │
                                        └───────────────────────┘
```

Слои:

* **`gstmast3rslam.py`** — точка входа gst-python: класс элемента + регистрация
  фабрики (`__gstelementfactory__`). Тяжёлые импорты (torch, mast3r_slam) —
  ленивые (в `do_start`), чтобы `gst-inspect` не тянул PyTorch при сканировании.
* **`mast3r_slam_gst/element.py`** — логика `BaseTransform` (caps, свойства,
  `do_transform_ip`, обработка EOS, сохранение результатов).
* **`mast3r_slam_gst/slam_runner.py`** — перенос логики `main.py` в класс
  (INIT/TRACKING/RELOC, backend-поток глобальной оптимизации, сохранение
  через `eval.save_*`). Использует `mast3r_slam.*` напрямую.
* **`mast3r_slam_gst/backends/`** — подключаемый инференс:
  * `torch_cuda.py` — обёртка над `load_mast3r`/`_encode_image`/`decoder`
    (по умолчанию);
  * `tensorrt_encoder.py` — TRT-движок только для энкодера, fallback на torch.
* **`mast3r_slam_gst/buffer_utils.py`** — Gst-буфер ↔ numpy (с учётом stride).
* **`mast3r_slam_gst/metadata.py`** — сборка `Gst.Structure` позы для шины.

### Свойства элемента

| Свойство | Тип | По умолчанию | Назначение |
|----------|-----|--------------|------------|
| `config` | string | `config/base.yaml` | YAML-конфиг SLAM |
| `calib` | string | `""` | YAML интринсики (вкл. `use_calib`) |
| `checkpoint` | string | `checkpoints/MASt3R_..._metric.pth` | веса MASt3R |
| `retrieval-checkpoint` | string | `..._retrieval_trainingfree.pth` | веса ретривера |
| `backend` | enum | `torch` | `torch` или `tensorrt` |
| `trt-encoder-engine` | string | `""` | путь к `.engine` энкодера (для `tensorrt`) |
| `device` | string | `cuda:0` | устройство |
| `save-dir` | string | `logs` | куда писать `.txt/.ply/keyframes` |
| `sequence-name` | string | `mast3rslam` | базовое имя выходных файлов |
| `save-results` | bool | `true` | сохранять ли по EOS |
| `conf-threshold` | double | `1.5` | порог уверенности для `.ply` |
| `backend-thread` | bool | `true` | глобальная оптимизация в фоновом потоке |
| `max-fps` | double | `0` (без лимита) | троттлинг (камера может быть быстрее инференса) |

## 5. Сборка в Docker (DeepStream 9.0)

`docker/Dockerfile` — `FROM nvcr.io/nvidia/deepstream:9.0-*` (триплет/тег задаётся
ARG). Внутри: GStreamer 1.24 уже в составе DeepStream 9.0 (Ubuntu 24.04),
доустанавливаются `python3-gi`, `gstreamer1.0-python3-plugin-loader`,
PyTorch с CUDA, сборка `mast3r_slam_backends` (`pip install -e .`), submodules
mast3r/dust3r/in3d, lietorch. Плагин монтируется в `GST_PLUGIN_PATH`.

> Примечание: на момент написания публично доступен DeepStream до 7.x. Тег
> `9.0` берётся как указано в задаче; в `Dockerfile` он вынесен в `ARG
> DS_VERSION`/`ARG BASE_IMAGE`, чтобы подставить реально доступный образ из NGC
> без правки остального.

## 6. Дальнейшие улучшения (вне минимального объёма)

* Zero-copy: маппинг NVMM-буфера в CUDA-указатель (через `pyds`/CuPy) и приём
  тензора прямо на GPU без перегонки RGBA в системную память.
* TensorRT и для декодера (две статические профили под два порядка) — при
  готовности пожертвовать бит-в-бит совпадением ради FPS.
* Привязка поз к буферам как `GstMeta` (а не только сообщения шины) для
  downstream-аналитики.
* Полноценный `nvdsmeta`-вывод для интеграции с трекерами DeepStream.
